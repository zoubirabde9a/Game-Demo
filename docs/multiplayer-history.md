# Multiplayer history

How online play was built, one step at a time. Each step left the game building, the tests passing and the game playable. The current picture is in [multiplayer-plan.md](multiplayer-plan.md); this file is the record of how it got there and is only appended to.

- [x] 1. Remove waves and levels. The map is a fixed arena; monsters wander and are topped back up to a fixed population when they die.
- [x] 2. Several players in the simulation. Players live in an array with per-player input, health, cooldowns, spawn point and score. Swords, fireballs and shockwaves damage other players (never their owner). Monsters target the nearest player.
    - [x] 2a. Player slots with per-slot input, spawn point and queued actions; keyboard mapped in `client/keyboard_input.cpp`; monsters chase the nearest player.
    - [x] 2b. Swords, fireballs and shockwaves damage other players (never their owner); kills and deaths credited to slots; HUD shows the local slot's score.
- [x] 3. Split simulation from rendering. A `SimulateTick(world, inputs[], dt)` updates every entity without drawing, playing sounds or touching assets; the client draws in a separate pass. Done: `code/sim/simulate.cpp` has `SimulateTick(AppState, Arena, DeltaTime)`; it reads `AppState->Players[i].Input`, writes sounds to `AppState->Events`, and never touches the renderer, assets or `app_input`. Drawing lives in `code/client/`.
- [x] 4. Headless server program (`code/server/`). Fixed-tick loop around `SimulateTick`, builds on Windows (for local testing) and Linux (for the VPS) with no graphics libraries. `code/server/sim_game.cpp` runs the real simulation behind `code/server/game_api.h`. It compiles `app_sim.cpp` (the shared state, the engine core and the simulation) and none of `client/`, `ui/` or the engine's rendering, OpenGL, sound, asset and widget code, so it links without OpenGL. Their types still reach it through `app_state` in `app.h`; splitting that struct into a simulation part and a client part is the remaining step.
- [x] 6. Server networking: `code/net/connections.h` (client slots, timeouts, new-input filtering) and `code/net/socket.h` (UDP on Windows and Linux), driven by `code/server/server.cpp`.
- [x] 5. Network protocol (`code/net/`). Packet layout for connect, input and snapshot, with serialization tests. `code/net/protocol.h` describes the packets; `code/tests/net_tests.cpp` checks them.
- [x] 7. Client networking. Connect to a server address, send input each frame, draw entities from snapshots, show other players' names and health. The connection itself is done: `code/net/client.h` connects with retries, sends inputs, keeps the newest snapshot and reports why a connection ended. The game uses it: put `a.b.c.d:port` in `build/server.txt` or the `GAME_SERVER` environment variable and `code/client/online.cpp` connects, sends the held keys each frame, and shows the connection state under the HUD.
    - [x] 7a. Connect from the game, send input, show status.
    - [x] 7b. While connected the world is drawn from the server's snapshot: `code/client/replicas.cpp` keeps one local replica per server entity Id (created, moved, recreated when the Id's type or look changes, removed when it leaves the snapshot); the arena itself is built identically on both sides and never sent. Snapshot entities carry a `Variant` byte (monster kind or shot style). `RunWorldTick` in `client/online.cpp` picks replicas or the local simulation and switches back to a fresh local game if the connection ends. Kills and deaths are not in the snapshot yet, so the online scoreboard shows zeros.
    - [x] 7c. Health and labels above other players, scores online. Each snapshot ends with every connected player's kills, deaths and monster kills (`net_score`, protocol GDM4) and a player entity's `Variant` is its slot, so `client/replicas.cpp` fills `AppState->Players[]` and the Tab scoreboard works online; `ui/hud.cpp` labels other players "Player N" above their health bar.
    - [x] 7d. Player-chosen names: set `GAME_NAME` or put the name on the second line of `build/server.txt`. The connect request carries it (protocol GDM5, at most 15 printable characters, cleaned on read), `GamePlayerNamed` stores it per slot, and each snapshot carries one player's name in turn (`NameSlot`), so every client has all names within 8 ticks. Labels and the scoreboard show it, or "Player N" without one.
    - [x] 7e. Monster details for replicas (protocol GDM6): each snapshot entity carries its elite `Affix`, a `Status` bitmask (bit N while status effect N + 1 runs) and the `Ability` index of a monster shot or hazard; Facing and Animation now share a byte and the three new fields share another, so a full snapshot is no bigger. Replicas get `EliteAffix`, `StatusTimers` (1.5 s while set, so pips do not blink as if expiring) and `AbilityIndex`; monster hazards get replicas sized from their ability. `static_assert`s in `server/sim_game.cpp` fail the build if an enum outgrows its bits.
- [x] 8. Scoreboard and match flow in the HUD: player list, kills, deaths, respawn timer. Done: hold Tab for `ui/scoreboard.cpp`; dead players wait `PLAYER_RESPAWN_SECONDS` (3 s) as inert bodies (`IsDeadPlayer`) with a countdown on screen. Names are "Player N" until the protocol carries names.
- [x] 9. Deploy the server to the VPS as a service that restarts on failure. Live on vps-eu (152.53.147.77:27015, ARM): `deploy/deploy.sh vps-eu` builds on the machine, installs the `game-demo` systemd service, and rolls back if `build/probe` cannot join; restart after a crash, the version gate and 8 bot players over the internet were checked there. See deploy/README.md.
- [x] 10. Client-side prediction for the local player, so movement feels instant despite latency.
    - [x] 10a. Each snapshot carries `InputTick`, the newest of that client's inputs the server had applied (protocol GDM7), so the client knows which of its inputs to replay.
    - [x] 10b. `code/client/prediction.cpp`: each frame's held buttons are recorded under the input tick they were sent with; between snapshots the local player's replica is moved by this frame's input through the same `UpdatePlayer` the server runs, and on each snapshot the inputs after `InputTick` are replayed from the server's position. Only movement is predicted; attacks, dashes and jumps wait for the server. A server test runs the real client loop against a real server: moving, the client leads by the inputs in flight; released, both rest within 1 unit. Corrections blend in, see step 14.
- [x] 11. Monster facing for front armour (protocol GDM8): each snapshot ends with up to 8 `net_facing` entries {entity index, angle in 256 steps of a turn} for monsters whose kind has `FrontArmor > 0`; replicas get `Direction` from it, which the shell is drawn from. `BlockFlash` stays server-only. A full snapshot still fits in 1200 bytes.
- [x] 12. Snapshots send what is nearest the viewer. The viewer's own player still goes first; the rest follow nearest first (`SimGameKeepNearest` in `server/sim_game.cpp`), so with more moving things than fit (48), the ones cut are the farthest away instead of whatever came last in the entity array.
- [x] 13. In-game connect screen (`ui/connect_screen.cpp`). F4 opens it, and it opens at launch when no server is configured. Type the address and name, then Connect, Cancel, Retry or Play offline; the status line shows the connection state, and the screen closes itself once joined. A connect from it rewrites `server.txt`. While it is open the keys type into it instead of moving the player (`KeysToUi`). `OnlineConnect`/`OnlineDisconnect`/`GetOnlinePhase` in `client/online.cpp` are what it calls. Typed text now comes from Windows character messages, so `.`, `:` and any keyboard layout work.
- [x] 14. Smooth corrections. When a snapshot's replay puts the local player somewhere other than where it was drawn, `client/prediction.cpp` keeps the difference as `DrawError` and draws the player that far off its predicted position, shrinking it by `PREDICTION_BLEND_RATE` (20 per second, under a tenth left after 100 ms). Movement and collision run from the predicted position. A correction longer than 4 tiles (a respawn) snaps. Holding a direction online, the drawn player trails the predicted one by under a unit.
- [x] 15. Sounds online (protocol GDMA). The server keeps the last 64 sound events (`server/event_relay.cpp`), each with where and on which tick it played. Each snapshot carries up to 8 of them (`SoundCount`, `Sounds[]`, asset type ids): the ones the viewer has not been sent yet and that played within `RELAY_HEARING_DISTANCE` (900 units) of its player. The client queues them in `AppState->Events` (`client/online.cpp`), where the local game's sounds go, so `PlaySimEvents` plays them. A lost snapshot loses its sounds.
- [x] 16. Kill events (protocol GDMB). `DamageEntity` emits `SimEvent_Kill` (victim slot, killer slot, or the monster kind that did it) whenever a player dies. The server relays them like sounds (`server/event_relay.cpp`) to every player once (`Kills[]`, up to 4 per snapshot); the client queues them with the local ones, and `PlaySimEvents` adds them to `AppState->KillFeed` (`client/kill_feed.cpp`: newest 5, gone after 6 s). Drawing the feed is the UI's job.
- [x] 17. Snapshots that do not fit. Every list full at once is more than 1200 bytes, and the server used to drop the whole snapshot silently. `NetWriteSnapshotFitting` now leaves out the farthest entities (and the abilities and facings that point at them) until it fits; the stats line counts `trimmed` snapshots.
- [x] 18. Other units glide between snapshots (`client/replica_smoothing.cpp`): each replica moves from where it is drawn to the newest snapshot position over one measured snapshot interval, so remote players and monsters show about 50 ms late but move evenly. New replicas, the local player and jumps over 4 tiles snap.
- [x] 19. The respawn countdown runs online: the client starts `PLAYER_RESPAWN_SECONDS` when a snapshot first shows a player dead (`client/replicas.cpp`), at most one snapshot behind the server.
- [x] 20. Reconnect by itself (`client/online.cpp`): a connection that ended because the server closed, the link went quiet or nobody answered retries 5 times, waiting 2 s more each time. A full server, a different build or leaving by choice do not retry.
- [x] 21. Same names told apart: the server gives a name already in use (ignoring case) " 2", " 3"... within 15 characters (`GamePlayerNamed`).
- [x] 22. The wire layout is pinned: `TestWireLayoutIsPinned` (net_tests.cpp) hashes one packet of every type and fails when the bytes change while `NET_PROTOCOL_ID` does not.
- [x] 23. The server builds without the client: `app_sim.cpp` is the shared state, the engine core (`engine/engine_core.cpp`) and the simulation; the server compiles only that and links without OpenGL.
- [x] 24. Join handshake (protocol GDMC). A join request without the right cookie gets a `ConnectChallenge` and takes no slot; the cookie is a hash of a server secret, the address, the salt and an 8.5 s window (`net/connections.cpp`), so the server stores nothing for strangers. Before this, packets with a forged source address could fill all 8 slots or reset a connected player's slot ("same address, new salt" counted as a restart). The client answers the challenge by itself (`net/client.cpp`).
- [x] 25. Session token (protocol GDMD). Every packet header carries `Token`, the client's salt, both ways. The server (`Strict`) ignores a known player's packets with another token, so forged inputs or goodbyes from a player's address do nothing; the client ignores packets without its token, so a forged "server closed" or snapshot does too. The header is 4 bytes longer; a full snapshot is trimmed as before.
